# Продакшн-архітектура UTEXO LSP (signet → mainnet-ready)

> Пропозиція. Базується на дослідженні поточного коду (utexo-lsp `origin/main`,
> rgb-lightning-node, rln-telegram-bot) та на досвіді налагодження regtest-флоу
> (lsp-regtest, async payments) у rgb-sdk-rn-demo.

---

## 1. Ключові принципи

1. **Жодних подарункових push-балансів.** LSP ніколи не передає RGB через
   `push_asset_amount` при відкритті каналу. Будь-який баланс (RGB і msat)
   користувач отримує як справжній Lightning-платіж через `lightning_receive`.
   Це: (а) trust-minimized — платіж верифікований, а не задекларований;
   (б) безпечно на віртуальних каналах `trusted_no_broadcast` (пуш до
   отримувача, який потім приймає HTLC, force-close'ить канал — перевірено
   на regtest); (в) дозволяє один конфіг для всіх сценаріїв.
2. **Чотири домени довіри** з мінімальними зв'язками: компрометація одного
   компонента не дає доступу до інших.
3. **Активи розподілені по багатьох алокаціях** — одна велика алокація на
   одному UTXO означає повну зупинку провіжинінгу при першій же pending- або
   застряглій операції (`InsufficientAssets` / stuck Initiated Send).
4. **Fail-closed автентифікація** між власними сервісами (`APAY_BEARER_TOKEN`),
   жодних секретів на мобільних клієнтах.

## 2. Топологія

```
                      ┌─────────────────────────────┐
                      │  TREASURY / ISSUER RLN-нода │  ← емісія активу, один раз
                      │  (офлайн, крім поповнень)   │
                      └──────┬───────────────┬──────┘
              on-chain RGB   │               │   on-chain RGB + BTC
              (інвентар,     ▼               ▼   (бюджет онбордингу)
               батчами)
               ┌─────────────────┐   ┌──────────────────────┐
               │  LSP RLN-нода   │   │  RLN-нода бота       │
               │  + utexo-lsp    │   │  + rln-telegram-bot  │
               │  (гаряча;       │   │  (гаряча; REST       │
               │   публічний     │   │   приватний;         │
               │   LDK-порт)     │   │   Telegram-facing)   │
               └────────┬────────┘   └──────────┬───────────┘
                        │      lightning_receive │
                        │◄── on-chain RGB ───────┘
                        │       (через проксі + ланцюг;
                        │        переносник інвойсу — користувач)
                        ▼
          LN-канали (віртуальні trusted_no_broadcast) до мобільних юзерів

        Спільна інфраструктура: bitcoind (signet) · electrs · rgb-proxy
```

### Компоненти

| Компонент | Роль | Стан | Публічна поверхня |
|---|---|---|---|
| **Treasury / Issuer** (RLN-нода) | Емісія активу; зберігання основного сапплаю; періодичні рефіли | Холодний (онлайн лише під час рефілів) | Немає |
| **LSP** (RLN-нода + utexo-lsp) | Канали до користувачів, lightning_receive, async payments (apay), LNURL | Гарячий | Лише LDK peer-порт (9735) + utexo-lsp API за TLS-проксі |
| **Faucet-бот** (RLN-нода + rln-telegram-bot) | Онбординг: видача RGB та BTC користувачам; продакшн-заміна regtest-фасета | Гарячий | Лише Telegram |
| **Спільна інфра** | bitcoind, electrs, rgb-proxy | — | rgb-proxy має бути доступний усім учасникам |

### Зв'язки (важливо: чого НЕМАЄ)

- **LSP ↔ бот: жодної прямої взаємодії.** Ні API-викликів, ні спільних
  секретів, ні LN-каналу. Бот платить on-chain на blinded-інвойс, який
  отримав від користувача; LSP сам помічає трансфер через проксі/індексер.
  Бот можна замінити будь-яким джерелом фінансування без змін на боці LSP.
- **Мобільний клієнт ↔ LSP:** публічний HTTP API utexo-lsp + LN P2P.
  Автентифікація apay-реєстрації — неявна, через pubkey ноди (Noise/LN
  транспорт). Клієнт не має жодних серверних токенів.
- **RLN-нода LSP ↔ utexo-lsp:** localhost; `--lsp-base-url` +
  `--lsp-bearer-token` = `APAY_BEARER_TOKEN` (fail-closed: порожній токен =
  все відхиляється; вимкнути неможливо — це by design).

## 3. Емісія активу: на treasury, ніколи на LSP чи боті

- `issueassetnia` виконується **один раз** на treasury-ноді. NIA = фіксований
  сапплай, перевипуску не існує: втрата гаманця емісії = смерть активу.
- Precision/ticker незмінні — визначаються до емісії.
- Розподіл: ~5–10% → робочий інвентар LSP; виважений бюджет → бот;
  решта лишається на treasury (мнемоніка + data-каталог в офлайн/HSM-сховищі).
- Гарячі ноди (LSP — публічний LDK-порт, бот — публічний Telegram) — найбільш
  атаковані машини; жодна не повинна тримати весь сапплай.
  Радіус ураження: LSP = робочий інвентар, бот = бюджет онбордингу.

## 4. Потоки коштів

### 4.1 Онбординг користувача / поповнення (в т.ч. покупець в apay)

```
1. Гаманець юзера → utexo-lsp: lightning_receive (LN-інвойс + rgbInvoice від LSP)
2. Юзер → бот (Telegram deep link t.me/<bot>?start=<invoice>): передає rgbInvoice
3. Бот: send_asset (/sendrgb) → on-chain RGB на адресу LSP
4. Крон utexo-lsp: бачить settled-трансфер → платить LN-інвойс юзера по каналу
   (юзер отримує RGB + msat як справжній HTLC)
```

Це той самий механізм для обох сценаріїв: «отримати перші RGB» і «поповнити
баланс перед оплатою» (apay buyer). Жодного push.

> Демо вже реалізує цю послідовність: `screens/apay/useApayFlow.ts`
> (`receiveAsset` → зовнішня on-chain відправка → `awaitReceiveSettlement`).
> У продакшні змінюється лише відправник: фасет-демон :3008 → нода бота.

### 4.2 Async payment (merchant offline)

```
1. Мерчант (заздалегідь): apayNew по LN P2P → Lightning Address на LSP
2. Покупець: LNURL-pay → hold-інвойс від LSP → платить (HTLC паркується на LSP)
3. Мерчант онлайн: lsp.connect() → LSP запитує outbound-інвойс → сетл по каналу
```

Вікно офлайну обмежене CLTV: `APAY_INBOUND_MIN_FINAL_CLTV_EXPIRY_DELTA`
рахується **в блоках** — калібрувати під каденс мережі (див. §6).

### 4.3 Рефіл інвентарю LSP з treasury

- Тригер — **поріг, не календар**: spendable RGB < тижневий прогноз онбордингів
  × `DEFAULT_CHANNEL_ASSET_AMOUNT`.
- Споживає інвентар лише відкриття каналів. lightning_receive для LSP
  RGB-нейтральний (+1 on-chain / −1 off-chain); кооперативні закриття
  повертають активи.
- **Формат батча: N окремих переказів, не один великий.**
  Кожен шматок = окремий `/rgbinvoice` (новий інвойс на кожен переказ —
  кожен ляже окремою алокацією на окремий UTXO) розміром кратним
  `DEFAULT_CHANNEL_ASSET_AMOUNT`. Орієнтир: 10–20 шматків на сесію.
  Причина: rgb-lib витрачає цілу алокацію як інпут; change неspendable до
  сетлу; застряглий трансфер блокує алокацію назавжди (до `failtransfers`).
  Одна велика алокація = одна невдала операція зупиняє весь LSP.
- Тим самим рейсом — **BTC** на капасіті каналів (`DEFAULT_CHANNEL_CAPACITY_SAT`
  + push_msat + комісії за кожен канал).

## 5. Безпека

| Секрет / поверхня | Правило |
|---|---|
| `APAY_BEARER_TOKEN` | Тільки сервер (RLN LSP ↔ utexo-lsp, localhost). Згенерувати `openssl rand -hex 32`. Ніколи не потрапляє в мобільний застосунок — власник токена може підробляти settlement-колбеки. |
| RLN REST (3001) | Тільки приватна мережа. **Без** `--disable-authentication` у проді; токен у `LSP_TOKEN`/`RGB_NODE_TOKEN`. |
| utexo-lsp API (8080) | За TLS reverse-proxy; rate limiting на LNURL та `/lightning_receive` (вони неавтентифіковані by design). |
| SDK `lspBearerToken` | Опціональний клієнтський токен для публічного API — **інший** trust-домен, ніколи не дорівнює `APAY_BEARER_TOKEN`. |
| Мнемоніки | Окрема на кожну ноду. Treasury — офлайн/HSM. Data-каталоги RLN = стан каналів: безперервний бекап, відновлення зі застарілого стану = втрата коштів. |
| Бот | Sybil-контроль через Telegram-акаунти + квоти на акаунт; бот роздає інвентар. |

## 6. Конфігурація (signet, блоки ~30 с)

Повний анотований env — у тредах деплою; тут ключові рішення:

| Параметр | Значення | Чому |
|---|---|---|
| `DEFAULT_VIRTUAL_OPEN_MODE` | `trusted_no_broadcast` | Мобільні клієнти створюються з `enableVirtualChannelsV0` і відхиляють стандартні канали. Глобально → **весь флот** клієнтів має бути virtual-enabled. |
| `DEFAULT_CHANNEL_PUSH_MSAT` | `2000000` (2000 sat) | ≈ 1% LDK-резерв: депозити юзера повністю spendable. Єдина «дотація» на юзера. |
| push RGB | **відсутній** | Див. §1. В `origin/main` utexo-lsp його й немає. |
| `DEFAULT_CHANNEL_ASSET_AMOUNT` | бізнес-рішення | Заблокований капітал на юзера = це × кількість юзерів. Модель: кілька × типовий платіж. |
| `DEFAULT_CHANNEL_CAPACITY_SAT` | `100000` | Мін. RGB-канал = 30 010 sat; 100k економить signet-BTC. |
| `MIN_CONFIRMATIONS` | `3` | При 30-с блоках 3 конфи = 90 с — захист від reorg майже безкоштовний (LSP платить LN проти on-chain депозиту цієї глибини). |
| `APAY_INBOUND_MIN_FINAL_CLTV_EXPIRY_DELTA` | `864` | Блоки! 864 × 30 с ≈ **7.2 год** — це майже протокольна стеля: LDK-платник відхиляє маршрути з сумарним CLTV > 1008 блоків (864 + 72 за хоп LSP = 936 < 1008). Вікно ~24 год на 30-с блоках неможливе без підняття `max_total_cltv_expiry_delta` на боці платника (зміна в SDK/RLN). На 10-хв мережі 144 ≈ 24 год. |
| `APAY_CLAIM_MARGIN_BLOCKS` | `120` | ≈ 1 год запасу при 30-с блоках (12 на 10-хв мережі). |
| `MIN_AMT_MSAT` | `3000000` | = HTLC-мінімум RLN для RGB; нижче не можна. |
| `UTXO_MIN_COUNT` / `TARGET` | `10` / `20` | Пул colorable UTXO = ліміт паралельності операцій + рознесення blind-receive по різних UTXO. |
| `CRON_EVERY` | `30s` | 5s — regtest-звичка. |
| `DATABASE_*` | sqlite на персистентному диску | Єдиний вкомпільований драйвер → один інстанс. Бекапи; ніколи не wipe'ати (на відміну від regtest-скриптів). |
| Бот `FEE_RATE` | `1–2` | У семплі стоїть 100 sat/vB — спалить бюджет. |
| Бот `ASSET_ID` | = `SUPPORTED_ASSET_IDS` | Узгодити. |

RLN-нода LSP: `--enable-virtual-channels-v0 --lsp-base-url http://127.0.0.1:8080
--lsp-bearer-token <secret>`, без `--disable-authentication`.
RLN-нода бота: **без** virtual/lsp-прапорців — звичайний on-chain відправник.

## 7. Моніторинг (мінімальний набір алертів)

1. **Stuck Initiated Sends** (вік pending-трансферів) — найбільший операційний
   ризик: кожен блокує colorable UTXO до ручного `failtransfers`; апстрім
   клінап-крону ще не має.
2. Spendable RGB на LSP < поріг рефілу (§4.3).
3. BTC-баланс LSP < (очікувані канали × капасіті + комісії).
4. Баланс бота (RGB + BTC) < бюджетний поріг.
5. Кількість colorable UTXO < `UTXO_MIN_COUNT`.
6. Вік apay-outbox проти CLTV-дедлайну (HTLC, що наближаються до таймауту).
7. Force-close події.
8. **Доступність rgb-proxy** — спільна артерія: кожен консайнмент
   (treasury→LSP, бот→LSP, LSP→юзер) іде через нього.
9. Ріст кількості каналів (поки крон відкриває канал кожному піру —
   див. §8.1 — аномальний ріст = дрейн ліквідності).

## 8. Відомі обмеження та пропозиції в upstream

1. **Крон відкриває канал кожному піру, що підключився** — без замовлення,
   оплати чи автентифікації. Мітигація зараз: не світити peer-адресу поза
   застосунками + алерт №9. Правильне рішення (PR в utexo-lsp): order-driven
   провіжинінг — канал лише у відповідь на автентифікований ордер
   (lightning_receive-мапінг, apay-реєстрація, явний channel order),
   LSPS1-стиль; глобальні `DEFAULT_CHANNEL_*` перетворюються на поліси-ліміти.
2. **Немає клінапу застряглих трансферів** — потрібен крон-степ
   `failtransfers` для звільнення заблокованих UTXO.
3. **sqlite-only** — один інстанс, без failover; додати Postgres-драйвер,
   коли виростуть вимоги до аптайму.
4. **Статичні fee-rate** — на mainnet-завантаженості потрібна естимація.
5. **`DEFAULT_VIRTUAL_OPEN_MODE` глобальний** — змішаний флот (частина
   клієнтів на стандартних каналах) конфігом не виражається; потрібні
   per-connection параметри.
6. Баг-репорт: гілка `inbound = 1_000_000 × 10^decimals` в
   `openChannelRequest` (api.go) запушила б мільйон юнітів, якби з'явився
   `/listconnections`.

## 9. Що вже зроблено в коді (статус)

- **utexo-lsp повернуто на `origin/main`** — локальний патч
  `DefaultChannelPushAssetAmount` + евристика порядку підключень видалені
  (збережені в git stash). Евристика була нестабільною (залежить від порядку
  підключень, ламає flow0) і непотрібною за цією архітектурою.
- **Демо apay-флоу** (`screens/apay/useApayFlow.ts`): покупець фінансується
  через lightning_receive top-up (фаза `a_topup`) замість push — це і є
  продакшн-послідовність.
- **Скрипти** (`start-lsp-regtest.sh` / `start-lsp-local.sh`): один конфіг для
  всіх флоу, без `DEFAULT_CHANNEL_PUSH_ASSET_AMOUNT`; додано
  `adb reverse tcp:3008`.
- Обидва regtest-флоу (lsp-regtest flow0 і apay) працюють на цьому конфігу —
  той самий, що пропонується для продакшну (з поправкою на мережеві значення §6).
